# 精度を上げる試行の記録

続きの作業と再開の手順は [next.md](next.md) にある。

人が確かめなくても正しく読める状態を目指して、策を1つずつ試した記録。
効いた策はコミットし、効かなかった策はここに結果と理由を残してコードは捨てる。

対象は PDF の楽譜 (きれいな印刷譜) だけ。写真・画面キャプチャ・手書きは対象外。

## 測り方

```bash
uv run --with music21 python make_truth.py       # 正解を作る (初回だけ)
uv run python bench.py raw --label=名前            # 校正なし。OMR の結果は取っておくので2回目からは数秒
uv run python bench.py full --yes-full --label=名前  # Claude を使う本番どおりの処理
uv run python bench.py full --yes-full --from=名前:段 --label=別の名前   # その run の結果を引き継ぎ、段から後ろだけをやり直す
```

- 正解は music21 のコーパスから作ったピアノ譜20曲。`test_` で始まる7曲は改善の判断に使わず、最後の確認だけに使う (`--test` を付けたときだけ測る)。
- 画像は2通り。Verovio で字体を曲ごとに替えて描いたもの (`verovio`) と、MuseScore 4 で PDF にしたもの (`musescore`)。
  どちらもアプリが PDF を取り込むときと同じく横2000px・JPEG 品質0.92 にする。
- 主な数字
  - right: 両手の音 (高さ・位置・長さ) が全部合っている小節の数。
  - silent: 間違っているのに「確かめきれなかった」印がない小節の数。人が確かめなくてよいと言えるのは、これが 0 のとき。
  - flag: 印の付いた小節の数 (人が確かめる必要がある数)。
- 毎回の数字は `bench/work/history.jsonl` に1行ずつ残る (Claude の呼び出しの回数とトークン数も)。
- 2026-11-24 から、結果の表に来歴が出る: 段ごとに直した小節と壊した小節の数、2つの読み取りの突き合わせの結果ごとの間違い、
  印を付けた段ごとの当たり外れ。途中のデータは `bench/work/runs/<名前>/<曲>_<条件>/` の `p{n}_at_<段>.musicxml` と `p{n}_trace.json` に残る。

## 試行

### 0. 基準 (2026-11-16)

PDF の条件に切り替えたときの出発点。dev は13曲 (696小節、2条件の合計)、test は7曲 (370小節)。

| 段階 | dev 合う小節 | dev 合う音 | test 合う小節 |
| --- | --- | --- | --- |
| homr だけ (raw) | 470/696 (67.5%) | 84.7% | 278/370 (75.1%) |

  声部の多い曲 (クララ・シューマンのポロネーズ) で崩れる。

### 2. Audiveris でも読み、小節ごとに突き合わせる: 採用

homr とは別の方法で読む OMR (Audiveris 5.11) を足し、鳴る音で小節を対応づけた。
homr の小節が拍子に合わず、Audiveris の小節が合うときだけ Audiveris の音に入れ替える。

| | dev 合う小節 | test 合う小節 |
| --- | --- | --- |
| homr 0.7.1 だけ (raw) | 521/696 (74.9%) | 303/370 (81.9%) |
| Audiveris と突き合わせ (raw) | 526/696 (75.6%) | 305/370 (82.4%) |

- Audiveris 単独 (homr 0.7.0 のころに測った) は 65.8% で homr より低いが、得意な曲が違う。
  コラールと、2声部が符頭を共有する beach_prayer は Audiveris が良く、それ以外は homr が良い。
- 2つが一致した小節は dev で398、そのうち381 (96%) が正解だった (homr 0.7.0 で測定)。
  どちらか一方が正しい小節は 583/696 (84%) で、食い違いの選び方しだいで上がる余地が大きい。
- 拍子に合うかで選ぶだけでは、伸びは小さい (両方とも拍子に合って食い違う小節が多い)。
- Audiveris は1ページ8秒ほど。入っていなければ homr だけで動く。

### 5. homr のタイを和音の共通音すべてに広げる: 採用

homr 0.7.1 はタイを `<tie>` で書くようになったが、和音のうち1音にしか付けない (メープルリーフ・ラグのオクターブの片方など)。
もう片方が弾き直しになっていた。以前スラーに対して入れていた「2つの和音の共通音をすべてタイでつなぐ」を、本物のタイにも当てた。

| | dev 合う小節 | test 合う小節 |
| --- | --- | --- |
| 前 (raw) | 526/696 (75.6%) | 305/370 (82.4%) |
| 後 (raw) | 570/696 (81.9%) | 323/370 (87.3%) |

- homr を 0.7.1 に上げたときにメープルリーフ・ラグが悪くなった (41 → 25 小節) のは、ほぼこれが原因だった。

採点の直し (2026-11-16): 曲の最初の小節は最初の音の位置を0にそろえる。dichterliebe2 の正解には、譜面に描かれない16分休符が
弱起の頭に入っていて、正しく読んだ結果も位置違いになっていた。この直しで raw の dev は 570 → 572。

正解の直し (2026-11-16): 同じ高さの2音をちょうどつなぐスラーはタイにした (make_truth.py の arcs_to_ties)。
譜面ではタイと見分けがつかず、弾く人もタイとして弾く。beach_prayer と dichterliebe2 の4音。raw の dev は 572 → 574。

### 6. 2つの OMR が一致した小節は、校正での書き換えを取り消す: 採用

### 7. 仕上がりをもう一度だけ写真と見比べ、違うと言われた小節に印を付ける: 採用

見比べ (verify) は1段につき1〜2割の確率で見落とすので、最後に別の回でもう一度見比べ、直さずに印だけ付ける (`audit_page`)。

| --- | --- | --- |
| なし | 27 | 30 (19) |
| あり | 22 | 49 (33) |

- 新しい印19のうち、本当に間違っていたのは5。間違いの見落としは2割減るが、印の当たりは悪い。
- 残る silent の大半は dichterliebe2 (8) と clara_polonaise1 (7)。2声部の符頭の共有と高音の加線で、見比べでも同じように読み違える。
  見比べを繰り返すだけでは減らないので、別の手がかりが要る。
- 1段につき Claude を1回多く呼ぶ。

直し (2026-11-16): homr のスラーをタイに直すとき、♮と♭の違いを見ていなかった (音名とオクターブだけで比べていた)。
シ♮からシ♭へのスラーまでタイにしていた。臨時記号も比べるようにした。校正なしの数字は変わらない。
正解の作成 (arcs_to_ties) も同じ関数を使っていたので、高さの違う音を結ぶタイが5曲に入っていた。作り直した (鳴る音は同じ)。

残る見落とし: clara_polonaise1 の 22→23 小節などは、段の終わりで切れた弧のあとに臨時記号のないシがあり、譜面の慣例ではシ♮のタイと読める。
正解 (music21 の元データ) はスラーで、次の音はシ♭。MuseScore が注意のための♭を付けないので、譜面だけでは読み分けられない。

### 11. Audiveris のタイを homr に移す: 採用

2つの音と同じ位置に homr も同じ高さの音を読んでいれば、homr の音もタイでつなぐ (`borrow_ties`)。

Claude なし (dev、両条件): 574 → 578 / 696。5小節が直り、1小節が悪化した。悪化は chorale_bwv66_6 で、
Audiveris がフェルマータの弧をタイと読み、それが移って2つの読みが一致してしまった (一致した間違いは 21 → 22)。

bwv66_6 の悪化は、本番の処理では直った。印の増加は主に clara_polonaise3 で、Claude の答えの揺れの範囲と見ている。

### 12. 弧の終わりが和音の別の音に付いていても、同じ高さの音があればタイとみなす: 採用

chopin_mazurka06_2 の 39→40、47→48 小節は、2分音符から次の小節頭の2声部の和音へのタイ。homr も Audiveris も弧の終わりを
下の声部の別の音 (ド♯やレ) に付けるので、高さが違う本物のスラーと扱っていた。弧の始まりの音が終わった時点の和音に
同じ高さの音があれば、タイに直すようにした。装飾音符は長さがないので対象から外した。

Claude なし (dev、両条件): 578 → 585 / 696。悪化した小節はない。一致したのに間違っている小節は 22 → 17。
直った小節: beach_prayer 27・28、chopin_mazurka06_2 39・40・47・48、dichterliebe2 15 (いずれも MuseScore 条件)。
正解の作成も同じ関数を使うので作り直したが、鳴る音は変わらなかった。
本番どおりの処理は回していない。悪化がなく、一致して間違う小節 (印なしで通る間違い) が減ったので、Claude の段では悪くならない。

### 14. 加線の多い高い音のある小節に印を付ける: 不採用 (数えただけ)

### 15. タイを和音の共通音に広げるのは、弧の始まりと同じ声部の音だけにする: 採用

chorale_bwv269 の 10→11、21→23 小節は、アルトだけがタイで、同じ時刻のソプラノも次の小節の頭で同じ高さを弾き直す。
タイを和音の共通音すべてに広げていたので、ソプラノまでつないでいた。homr も Audiveris も同じに読むので、一致した間違いとして
印なしで通っていた。共通音に広げるのは、弧の始まりの音と同じ声部の音だけにした。終わりの側は声部を問わない
(12 のとおり、弧の終わりは別の声部の音に付いていることがある)。

Claude なし (dev、両条件): 585 → 595 / 696。悪化した小節はない。一致したのに間違っている小節は 17 → 7。
正解の作成も同じ関数を使うので作り直して比べたが、鳴る音は変わらなかった (ファイルは描画を変えないよう元のものを残した)。

メモ: 12 の変更で正解を作り直すと、beach_prayer の正解の弧が1つスラーからタイに変わる (鳴る音は同じ)。
正解の更新時刻が変わると試験台が譜面の画像を描き直し、過去の結果と比べられなくなるので、正解ファイルと画像は元のまま残している。

### 16. Audiveris から移したタイのある小節は「一致」と扱わない: 採用

試験用の曲 (test_) で Claude なしの結果を見ると、11 (タイを移す) は 1小節直して4小節悪くしていた (test_clara_polonaise4)。
Audiveris が弧のないところにタイを付け、それが移って2つの読みが一致するので、印なしで通る間違いになる。
dev と test を合わせると、タイを移した小節の正しさは7割ほどで、一致した小節 (99%) よりずっと低い。
そこで、タイを移した小節は音が同じでも一致とせず、校正から守らず最後の見比べにかける側に入れた。Claude なしの正しさは変わらない。

| dev + test (両条件) | 一致した小節 | そのうち間違い |
| --- | --- | --- |
| 移したタイも一致と扱う | 687 | 10 |
| 扱わない | 677 | 6 |

Claude なしの正しさ: dev 595 / 696、test 324 / 370 (今日の4つの変更の前の test は 323)。

### 23. PDF に文字として入っている符頭とタイを読み、データと食い違う小節に印を付ける: 採用

楽譜ソフトが書き出した PDF には、符頭・臨時記号が音楽用の字体 (SMuFL) の文字として、五線・小節線・タイの弧が線として、正確な座標で入っている。
画像にした時点でこの情報を捨てていた。`glyphs.py` が PDF から小節ごとの符頭 (種類と高さ) とタイの始まる音を読み、データの音符の

- 読み取りの検算: 正解のデータと、その正解から作った PDF を比べる。dev の 348 小節のうち食い違うのは 9 小節
  (同じ高さの音が2つの声部にある箇所の描き方、和音のタイの対応)。これは合っている小節に付く誤った印になる。
- pdfium は、同じ文字がすぐ近くに重なると (和音の隣の符頭など) 文字を返さない。大きさと濃さの近い既知のグリフとみなして補った。
- 同じ高さの音で始まって終わるスラーをタイと読み違えた (clara_polonaise3 の5小節)。あいだに音があり、弧の端が符頭から離れていればスラーとした。
- 加線の多い音は隣の段に近いので、五線から符頭まで加線が途切れず続く側の段のものとした。
